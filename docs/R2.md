# Cloudflare R2 — armazenamento de arquivos

Runbook da saída do disco local para o object storage. Cobre a convenção de
chaves, a ordem dos passos em produção, o que fazer quando a migração falha no
meio e como reverter.

**Há dados reais em produção.** A ordem dos passos abaixo não é sugestão: ela é
o que faz o sistema atravessar a migração sem uma janela em que anexo nenhum
some. Executar fora de ordem — em especial migrar antes de fazer o deploy —
quebra imagem de catálogo e ficha de cliente para todo mundo.

---

## 1. O problema que isto resolve

Hoje todo anexo do sistema vive em dois diretórios planos no servidor:

```
backend/src/data/uploads/           imagem de joia, banner, logo, foto de profissional
backend/src/data/private-uploads/   comprovante, foto clínica, PDF de termo
```

São **compartilhados entre todas as clínicas**: o nome do arquivo é 32
hexadecimais aleatórios e nada no caminho diz de quem ele é. Sobrevivem aos
deploys porque `scripts/deploy.sh:146`
exclui os dois diretórios do rsync — o que também significa que **essa é a única
cópia que existe**.

O R2 resolve as duas coisas de uma vez: separa por clínica no próprio caminho do
objeto e tira os arquivos do disco de uma máquina só.

---

## 2. Convenção de chaves

A fonte da verdade é `backend/src/services/storage/keys.js`. Nenhum código monta
chave à mão — todo mundo chama `buildKey()`, inclusive o migrador.

```
BUCKET PÚBLICO   tenant_<id>/<categoria>/<arquivo>
                 plataforma/<categoria>/<arquivo>     landing da Monitence

BUCKET PRIVADO   tenant_<id>/<pasta>/<arquivo>        pasta derivada do purpose
                 orfaos/<arquivo>                     sem dono identificável
```

`<id>` é o **id inteiro** do tenant, o mesmo que nomeia o schema Postgres —
nunca o slug, que a clínica pode trocar e levaria embora o caminho de todos os
arquivos dela.

**Categorias do bucket público** (lista fechada): `joias`, `catalogo`,
`banners`, `logo`, `geral`.

**Pastas do bucket privado** saem do `private_files.purpose`. A regra é
"pasta = purpose", com **uma exceção que importa**:

| `purpose` no banco    | pasta no bucket    |
|-----------------------|--------------------|
| `digital_term`        | **`termos`**       |
| `appointment_reference` | `appointment_reference` |
| `public_booking`      | `public_booking`   |
| `medical_record`      | `medical_record`   |
| `postcare_photo`      | `postcare_photo`   |

O apelido `digital_term → termos` mora no mapa `PURPOSE_FOLDERS` de `keys.js`.
É por isso que ninguém pode concatenar chave à mão: quem escrever
`tenant_7/digital_term/x.pdf` grava num lugar que `GET /api/private-files/:filename`
não procura, e o PDF do termo some da tela sem erro nenhum no log.

### Quem é o dono de cada arquivo

O migrador **não adivinha pelo nome**. Ele pergunta ao banco:

| Tipo | Fonte da verdade |
|---|---|
| **Privado** | `private_files`, que vive **dentro** do schema `tenant_<id>`. O arquivo é da clínica em cujo `private_files` a linha aparece. |
| **Público** | varredura de **toda** coluna de texto/JSON dos schemas atrás de `/uploads/<arquivo>`. A clínica em cujo schema a referência aparece é a dona; a coluna que referencia define a categoria. |
| **Plataforma** | `platform.landing_sections.content` — imagens da landing da Monitence, de clínica nenhuma. Vão para `plataforma/geral/`. |
| **Órfão** | está no disco e nenhuma linha o referencia. Vai para `orfaos/` no bucket **privado**. |

Três decisões que valem ser ditas em voz alta:

- **`platform.tenants.logo_url` vai para `tenant_<id>/logo/`, não para
  `plataforma/`.** A linha carrega o id da clínica: o logo é dela, ainda que a
  coluna more no schema da plataforma. Seguir o dono real é o que mantém a
  regra "o caminho diz de quem é" válida sem exceção.
- **Órfão vai para o bucket privado.** Sem dono conhecido não dá para pendurar
  no prefixo de clínica nenhuma, e servir publicamente um arquivo de origem
  desconhecida é o pior dos dois mundos — pode ser foto clínica. Em `orfaos/`
  ele fica recuperável por um humano e invisível para a web.
- **A mesma imagem em duas categorias vira dois objetos.** Uma foto usada como
  joia e como banner é copiada para `tenant_1/joias/x` **e** `tenant_1/banners/x`,
  e cada coluna passa a apontar para a sua. Custa alguns KB e elimina a pergunta
  "de quem é esta imagem, afinal".
- **Legado de agendamento é privado.** `appointments.reference_photo_url` e
  `appointments.payment_proof_url` existiam antes do upload privado e ainda
  podem apontar para `/uploads/`. O migrador não os manda ao CDN: cria a linha
  correspondente em `private_files`, sobe sob `appointment_reference/` e troca
  a URL por `/api/private-files/<arquivo>`.

### Nota sobre as categorias no código de hoje

`routes/uploads.js:16` passa `category: "geral"` fixo, e `routes/landing.js:107`
não passa categoria nenhuma (cai em `geral`). Ou seja: **hoje nenhuma rota grava
em `joias`, `catalogo`, `banners` ou `logo`** — só a migração usa essas
categorias, a partir da coluna que referencia o arquivo.

Migrar em categorias produziria um bucket meio organizado: os arquivos antigos
classificados, os novos todos em `geral`. É o pior dos dois mundos.

**Decidido em 04/08/2026: a migração é achatada, e isso virou o PADRÃO do
script.** Todo público vai para `<tenant>/geral/`, igual ao que o código produz
hoje. `--categorias` reverte, mas só faz sentido junto com ensinar
`routes/uploads.js` a receber a categoria — e aí é uma rodada própria, que mexe
nos pontos do frontend que sabem o contexto.

Conviver com os dois formatos depois não incomoda: as URLs públicas ficam
absolutas no banco, então organizar por categoria mais tarde **não exige
re-migrar** o que já subiu.

## 3. A ORDEM DOS PASSOS

> Do 1 ao 8, sem pular. O passo 3 antes do 6 é o que evita a janela de quebra.

### Passo 1 — Criar os buckets e o domínio na Cloudflare

1. R2 → **Create bucket**, dois buckets:
   - `aura-clinic-public`
   - `aura-clinic-private`
2. No bucket **público**: Settings → **Public access** → conectar um domínio
   (ex.: `cdn.seudominio.com.br`). É esse domínio que vai parar dentro das URLs
   gravadas no banco.
3. No bucket **privado**: **não** conectar domínio nenhum, **não** habilitar
   acesso público. Ele é lido só pela API, em `GET /api/private-files/:filename`,
   que confere papel e propósito antes de deixar o byte passar.
4. R2 → **Manage API Tokens** → token com permissão de **leitura e escrita** nos
   dois buckets. Anote `Access Key ID`, `Secret Access Key` e o endpoint
   `https://<conta>.r2.cloudflarestorage.com`.

> O domínio público entra nas URLs **do banco**. Trocá-lo depois exige outra
> passada de reescrita — escolha o definitivo agora.

### Passo 2 — Configurar os secrets

No `.env` do servidor (que o rsync do deploy exclui de propósito) e nos secrets
do GitHub Actions:

```
R2_ENDPOINT=https://<conta>.r2.cloudflarestorage.com
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_BUCKET_PUBLIC=aura-clinic-public
R2_BUCKET_PRIVATE=aura-clinic-private
R2_PUBLIC_BASE_URL=https://cdn.seudominio.com.br
```

**O conjunto é indivisível.** `config/index.js` derruba o boot em produção se
faltar qualquer um deles com os outros presentes: meia configuração produz
upload que "funciona" e devolve URL quebrada, ou arquivo privado gravado num
bucket que não existe. Sem nenhuma delas, o sistema segue no disco local, como
sempre foi.

Confira no boot da API — a linha sai sempre:

```
[storage] Cloudflare R2 ATIVO (público: ... privado: ...)
```

### Passo 3 — Deploy do código PRIMEIRO

```bash
bash scripts/deploy.sh
```

**Por que antes da migração:** a camada nova escreve só no bucket, mas na
**leitura** tenta o bucket e **cai no disco local** quando o objeto ainda não
está lá (`services/storage/index.js`, `getPrivateStream`). O `/uploads` estático
continua no ar (`src/index.js`) servindo as URLs relativas que o banco ainda
tem.

Resultado: no intervalo entre este passo e o passo 6, **nada quebra**. Upload
novo já vai para o R2; arquivo antigo continua saindo do disco. É esse fallback
que transforma a migração de uma operação de risco em uma cópia sem pressa.

Faça o caminho inverso (migrar antes de deployar) e as URLs do banco apontam
para um CDN que o código ainda não conhece, com os arquivos fora do lugar onde
o código antigo procura.

### Passo 4 — Backup dos anexos

No servidor, com o backend em `/home/auraclinic/backend`:

```bash
npm --prefix /home/auraclinic/backend run backup:uploads
```

Gera `backend/backups/uploads_<timestamp>.tar.gz` e **verifica o que gravou**:
`tar -tzf` (que lê o gzip inteiro e valida o CRC), contagem de arquivos contra o
disco, checksum SHA-256 e checagem de espaço livre antes de começar. Qualquer
problema **aborta com código de saída diferente de zero** e apaga o `.tar.gz`
parcial — não existe `|| true` nenhum ali, e o cabeçalho do script explica por
quê (`scripts/deploy.sh:232` engole a falha do `pg_dump` desse jeito, e um
backup que mente é pior do que backup nenhum, porque autoriza o passo seguinte).

Se os uploads estiverem num volume Docker montado fora de `src/data`:

```bash
UPLOADS_DIR=/mnt/dados/uploads PRIVATE_UPLOADS_DIR=/mnt/dados/private-uploads \
  bash backend/scripts/backup-uploads.sh
```

**Copie o `.tar.gz` para fora da máquina.** Um backup que só existe no servidor
que pode pegar fogo não é backup.

> Faça também o dump do banco (`npm --prefix backend run backup`): o passo 6
> reescreve colunas de URL, e é do dump que se volta se a reescrita sair errada.

### Passo 5 — `--dry-run` e conferência

```bash
npm --prefix backend run migrate:r2 -- --backup=backend/backups/uploads_<ts>.tar.gz
```

Dry-run é o **padrão**: sem `--apply` o script não escreve em lugar nenhum — nem
no bucket, nem no banco, nem no disco — e nem chega a construir o cliente do R2.

Ele imprime o plano inteiro: quantos arquivos, a chave de destino de cada um,
quantos órfãos, quantas linhas de banco seriam reescritas, e grava um relatório
JSON + CSV em `backend/backups/`.

**Confira antes de seguir:**

- [ ] O número de arquivos bate com o que há em disco (`ls | wc -l` nos dois diretórios).
- [ ] Cada clínica aparece com um número plausível de arquivos.
- [ ] Os PDFs de termo vão para `tenant_<id>/**termos**/…` — não para `digital_term/`.
- [ ] A quantidade de **órfãos** faz sentido. Muito órfão é sinal de que uma
      coluna escapou da varredura: rode de novo com `--scan-all-columns`.
- [ ] As **referências quebradas** (linha aponta para arquivo que não existe) são
      poucas e conhecidas. Não é erro fatal — essas URLs não são reescritas.
- [ ] Zero **colisões de chave** (o script recusa rodar se houver).

Opções úteis:

| Flag | Para quê |
|---|---|
| `--scan-all-columns` | varre toda coluna de texto/JSON, não só as de nome sugestivo. Mais lento, pega coluna esquecida. |
| `--only-tenant=<id>` | migra uma clínica só. Bom para o primeiro `--apply`. Nesse modo os órfãos são apenas listados, nunca migrados (a varredura é parcial e "órfão" ainda não quer dizer nada). |
| `--categorias` | usa `joias`/`catalogo`/`banners`/`logo` em vez de jogar todo o público em `geral`. **Não é o padrão** — ver a nota do capítulo 2. |
| `--uploads-dir=` / `--private-uploads-dir=` | quando os anexos estão num volume montado fora de `src/data`. |
| `--concurrency=N` | uploads simultâneos (padrão 4). |

### Passo 6 — `--apply`

Comece por uma clínica pequena:

```bash
npm --prefix backend run migrate:r2 -- --backup=... --apply --only-tenant=3
```

Confira essa clínica no navegador (catálogo, ficha de cliente, PDF de termo) e
só então rode o resto:

```bash
npm --prefix backend run migrate:r2 -- --backup=... --apply
```

O que acontece, nesta ordem:

1. **Sobe cada objeto** e **confere byte a byte**: `HeadObject` devolve o
   tamanho e o ETag, que no R2 é o MD5 do corpo para um `PutObject` simples (o
   caso aqui, sempre). Só é considerado migrado o que bate em tamanho **e**
   hash. Objeto que já está lá e confere é pulado, sem re-upload.
2. **Reescreve as URLs públicas** de `/uploads/<arquivo>` para a URL absoluta do
   CDN, **uma transação por schema** — uma falha na clínica 12 não desfaz as 11
   que já deram certo, e nenhuma clínica fica meio reescrita. A exceção são os
   dois campos legados de agendamento: viram URL autenticada de arquivo privado.
3. Só reescreve a URL de arquivo que **subiu e foi verificado**. O que falhou
   continua com `/uploads/…` e continua sendo servido pelo disco.

**Arquivos privados não têm reescrita**, de propósito: a chave é derivada de
tenant + purpose + filename, e a rota de leitura reconstrói a mesma chave. Eles
só precisam ser copiados. A única exceção é o legado de agendamento descrito
acima, pois ele ainda trazia URL pública e precisa ser promovido a
`private_files`.

A substituição usa `regexp_replace` com lookahead negativo, não `replace`. Um
`replace(valor, '/uploads/abc', …)` também casaria dentro de `/uploads/abcdef` e
corromperia a URL do vizinho.

**O disco nunca é apagado.** Não há uma única chamada de remoção no script.

### Passo 7 — Verificação

```bash
# nenhuma coluna deve mais apontar para /uploads/ (fora as referências quebradas conhecidas)
psql "$DATABASE_URL" -c "SELECT count(*) FROM tenant_1.jewelry_inventory WHERE image_url LIKE '/uploads/%'"

# o relatório tem a lista completa: o que foi, para onde, o que ficou órfão, o que falhou
cat backend/backups/migracao-r2-apply-*.json | head -40
column -s, -t backend/backups/migracao-r2-apply-*.csv | less
```

No navegador, com o cache limpo:

- [ ] Catálogo público carrega as imagens (as URLs devem vir de `cdn.…`).
- [ ] Logo da clínica aparece no painel.
- [ ] Foto de profissional aparece.
- [ ] **PDF de termo abre** (`/api/private-files/<arquivo>`) — é o teste do
      apelido `digital_term → termos`.
- [ ] Comprovante de pagamento e foto clínica abrem.
- [ ] Upload **novo** funciona e devolve URL do CDN.
- [ ] Banner do catálogo aparece.

Deixe rodar **algumas semanas** assim. Enquanto o disco existir, qualquer erro
de chave é invisível para o usuário (o fallback cobre) — e é justamente por isso
que ele precisa ficar.

### Passo 8 — Limpeza do disco (muito depois, e por decisão humana)

**Não faça isto no mesmo dia. Nem na mesma semana.**

O disco é a rede de segurança *e* o fallback de leitura. Enquanto ele existir,
uma chave errada é um incidente que ninguém percebe; sem ele, é uma imagem
quebrada na tela do cliente.

Antes de apagar qualquer coisa, tudo isto tem de ser verdade:

- [ ] O relatório da migração fecha: zero falhas, órfãos todos explicados.
- [ ] Nenhuma coluna do banco aponta mais para `/uploads/` (fora as quebradas
      conhecidas).
- [ ] Semanas de operação normal sem chamado de imagem ou anexo que não abre.
- [ ] O `.tar.gz` do passo 4 está guardado **fora** do servidor.
- [ ] Alguém conferiu no painel do R2 que a contagem de objetos bate com a do
      relatório.

Só então, e em duas etapas: mova para um diretório de quarentena (`mv`, não
`rm`) e espere mais um ciclo antes de apagar de verdade. Quando o disco sumir,
`app.use("/uploads", express.static(...))` em `src/index.js` pode sair junto.

## 4. Se a migração falhar no meio

**Rode o script de novo.** Ele foi feito para isso, e não há passo de limpeza
manual antes.

O que sustenta a retomada:

| Situação | O que acontece na segunda execução |
|---|---|
| Morreu durante os uploads | Objeto já no bucket é conferido por `HeadObject` (tamanho + MD5) e **pulado**. Só sobe o que falta. |
| Morreu entre o upload e a reescrita | Objetos são pulados; a reescrita roda normalmente. |
| Morreu **durante** a reescrita de um schema | A transação daquele schema sofreu `ROLLBACK` — ninguém fica meio reescrito. Os schemas anteriores já estão commitados e consistentes. A reescrita daquele schema roda de novo do zero. |
| Um arquivo específico falhou (ilegível, corrompido) | Os outros seguem — um arquivo ruim não aborta a migração inteira. A URL dele **não** é reescrita, continua em `/uploads/` e continua funcionando pelo disco. Sai no `failures` do relatório, e o processo termina com código **2**. |
| Rodou inteiro e alguém rodou de novo | Zero uploads, zero reescritas. As URLs já são do CDN e não casam mais com `/uploads/`; os arquivos já migrados são reconhecidos como tendo dono e **não** viram órfãos. |

Há ainda um **ledger** append-only em
`backend/backups/migracao-r2-ledger.jsonl` com uma linha por objeto verificado.
Ele é atalho e trilha de auditoria — quem manda é sempre o `HeadObject` no
bucket, então perder o ledger não atrapalha nada.

**O que nunca acontece:** perda de arquivo. O disco não é tocado em nenhum
cenário.

## 5. Como reverter

O ponto que torna a reversão barata é que **nada foi apagado**: os arquivos
continuam no disco e o R2 é uma cópia.

**Reversão total (voltar para o disco):**

1. Apague (ou comente) `R2_BUCKET_PUBLIC` e `R2_BUCKET_PRIVATE` do `.env` do
   servidor e reinicie a API. `config/index.js` desliga o R2 inteiro e a
   aplicação volta a gravar e ler do disco local — o boot passa a avisar
   `[storage] R2 desligado: arquivos gravados no DISCO LOCAL`.
2. As URLs **já reescritas** continuam apontando para o CDN. Enquanto o bucket
   público existir, elas seguem funcionando; o que muda é que upload novo volta
   a ser `/uploads/…`. Para desfazer a reescrita também, restaure o dump do
   banco do passo 4 — ou reescreva de volta:

   ```sql
   -- por schema, dentro de uma transação, e SÓ se você tem certeza
   BEGIN;
   UPDATE tenant_1.jewelry_inventory
      SET image_url = regexp_replace(image_url,
            '^https://cdn\.seudominio\.com\.br/tenant_1/[a-z]+/', '/uploads/')
    WHERE image_url LIKE 'https://cdn.seudominio.com.br/%';
   -- confira o SELECT equivalente antes do COMMIT
   COMMIT;
   ```

3. Se algum arquivo tiver sumido do disco (não deveria — o script não apaga),
   restaure do `.tar.gz`:

   ```bash
   tar -xzf backend/backups/uploads_<ts>.tar.gz -C /tmp/restauracao
   # confira o conteúdo antes de copiar por cima de qualquer coisa
   ```

**Reversão parcial (a chave de um arquivo saiu errada):** corrija a coluna do
banco à mão, ou apague o objeto do bucket e rode o migrador de novo — ele
reenvia o que não estiver lá.

## 6. Referência rápida

```bash
# backup dos anexos (obrigatório antes de migrar)
npm --prefix backend run backup:uploads

# dry-run: imprime o plano, não escreve nada
npm --prefix backend run migrate:r2 -- --backup=backend/backups/uploads_<ts>.tar.gz

# uma clínica só, para valer
npm --prefix backend run migrate:r2 -- --backup=... --apply --only-tenant=3

# tudo, para valer
npm --prefix backend run migrate:r2 -- --backup=... --apply

# ajuda
npm --prefix backend run migrate:r2 -- --help
```

| Código de saída | Significado |
|---|---|
| `0` | tudo certo |
| `1` | recusou rodar (sem backup, backup velho, R2 mal configurado, colisão de chave) |
| `2` | rodou, mas houve falhas — veja `failures` no relatório e rode de novo |

**Arquivos envolvidos:**

| Arquivo | Papel |
|---|---|
| `backend/src/services/storage/keys.js` | convenção de chaves — fonte única da verdade |
| `backend/src/services/storage/index.js` | camada de acesso (R2 com fallback no disco) |
| `backend/scripts/backup-uploads.sh` | backup verificado dos anexos |
| `backend/scripts/migrate-uploads-to-r2.mjs` | o migrador |
| `backend/backups/migracao-r2-*.json` / `.csv` | relatório: o que foi, para onde, o que ficou órfão, o que falhou |
| `backend/backups/migracao-r2-ledger.jsonl` | ledger de retomada |
